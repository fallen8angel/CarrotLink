# C3 vs C4 카메라 파이프라인 차이점 분석

> 작성일: 2026-03-20
> 목적: C3/C4 기기 간 카메라 스트리밍 품질 차이의 근본 원인 분석

---

## 1. 배경

- C3 유저는 카메라가 정상적으로 동작하는 반면, C4 유저는 카메라 끊김 및 검은화면 반복을 보고하고 있음
- 동일한 CarrotLink/Sidecar 코드를 사용하는 환경에서 C3는 정상 동작하나, C4에서만 문제가 발생함
- 이는 CarrotLink 앱 자체의 문제가 아닌, C3/C4 기기 측 인코딩 파이프라인의 구조적 차이에서 기인하는 것으로 분석됨

---

## 2. 확인된 구조적 차이 (확실한 근거)

### 2.1 H.264 인코딩 프리셋 차이 (가장 큰 영향)

| 항목 | C3 | C4 |
|------|----|----|
| 파일 | `ffmpeg_encoder.cc` | `ffmpeg_encoder.cc` |
| 프리셋 | `preset=ultrafast` | 프리셋 없음 (기본값 `medium` 사용) |
| 튜닝 | `tune=zerolatency` | 튜닝 없음 |
| 프레임 크기 | 작음 | 더 큼 |
| 인코딩 지연 | 최소 | 더 김 |

**영향:**

- C3의 `ultrafast` + `zerolatency` 조합은 인코딩 속도를 최우선으로 하여 프레임 크기가 작고 지연이 최소화됨
- C4는 프리셋이 지정되지 않아 FFmpeg 기본값인 `medium`이 적용되며, 이는 압축 효율을 높이는 대신 인코딩에 더 많은 시간과 리소스를 소비함
- C4에서 생성된 프레임은 크기가 더 커서 폰의 MediaCodec 디코더에 더 큰 부하를 주며, 중저가 폰에서 디코딩 드롭이 발생함

### 2.2 메시징 큐 크기 차이

| 항목 | C3 | C4 |
|------|----|----|
| 큐 크기 시스템 | 구분 없이 기본값 사용 | QueueSize 시스템 도입 |
| livestreamRoadEncodeData | 기본값 | 2MB (MEDIUM) |
| roadEncodeData | 기본값 | 10MB (BIG) |

**영향:**

- C4는 `livestreamRoadEncodeData`에 2MB라는 비교적 작은 큐 크기를 할당함
- 이로 인해 프레임 백프레셔(backpressure)가 발생하여 프레임 드롭이 일어날 수 있음
- 특히 인코딩 프리셋 문제(2.1)와 결합될 경우, 더 큰 프레임이 더 작은 큐에 쌓이면서 드롭 확률이 크게 증가함

### 2.3 코덱 선택 방식 차이

| 항목 | C3 | C4 |
|------|----|----|
| 선택 방식 | 정적 | 동적 |
| 결정 시점 | 시작 시 한번 결정 | 매 프레임마다 결정 |
| 결정 기준 | `encoder_info.encode_type` | `get_settings(in_width)` |

**영향:**

- C3는 인코더 시작 시 코덱을 한번 결정하고 스트림 전체에서 동일한 코덱을 사용함
- C4는 `get_settings(in_width)`를 통해 매 프레임마다 코덱을 결정하므로, 스트림 중간에 코덱이 변경될 수 있음
- 스트림 도중 코덱이 변경되면 폰 측 디코더에서 desync(동기화 해제)가 발생할 수 있음

### 2.4 하드웨어 매크로 차이

| 항목 | C3 | C4 |
|------|----|----|
| 컴파일 매크로 | `QCOM2` | `__TICI__` |
| 인코더 선택 | V4L / FFmpeg 중 선택 | V4L / FFmpeg 중 선택 |

**영향:**

- 서로 다른 하드웨어 매크로를 사용하여 조건부 컴파일이 이루어지므로, 동일한 소스 코드에서도 실제 선택되는 인코더 경로가 다를 수 있음
- 기기별로 V4L과 FFmpeg 중 어떤 인코더가 실제로 사용되는지 확인이 필요함

## 3. 로그 근거

### C4 유저 로그 (문제 발생)

```
packetsWindow: 20, decodedWindow: 1, dropsWindow: 19
```

- 20개 패킷 중 19개가 드롭됨 (95% 드롭률)
- 디코더가 유입되는 프레임 속도를 따라가지 못하고 있음을 명확히 보여줌

```
c4ReaderPressureRisk: true
```

- C4 기기 측 읽기 큐에 백프레셔가 발생하고 있음을 나타냄

### C3 유저 로그 (정상 동작)

- 동일한 네트워크 환경, 동일한 CarrotLink 버전에서 정상 동작 확인
- 드롭률이 극히 낮거나 0에 가까움

### 검은화면 유저

- bootstrap 프로파일(`p1c4`)에 머물러 있어 카메라 relay 자체가 시작되지 않은 경우 확인됨
- 이 경우 프레임 드롭이 아닌, 스트림 자체가 열리지 않은 상태임

## 4. 적용된 CarrotLink/Sidecar 측 완화 조치

C4 카메라 문제에 대응하여 CarrotLink 및 Sidecar 코드에 다음과 같은 완화 조치를 적용함:

### 디코딩 안정화

- `codecBacklogLimit` 1 → 2로 증가
- `decodeTaskBacklogLimit` 1 → 2로 증가
- `dequeueInputBuffer` 전 `drainOutput` 선행 호출 추가
- `pendingFrames` 큐 크기 12개로 제한 + sync count 보정

### 연결 안정화

- hard reconnect timeout 24s → 12s로 단축
- OkHttp `readTimeout` 15s + `pingInterval` 5s 추가
- provisional sync 타이머 4s → 2.5s로 단축
- WebSocket timeout 4s → 2.5s로 단축

### 프레임 관리

- Sidecar queue full 시 keyframe 보호 로직 추가
- FPS cap 드롭 시에도 타이머 업데이트 유지

### 프로파일 전환 안정화

- 프로파일 전환 시 카메라 유지 (soft reset 방식)
- debounce 억제를 통한 불필요한 재시작 방지

## 5. C4 브랜치 측 권장 개선사항

C4 기기 측 코드에서 다음 변경을 권장함:

### 5.1 FFmpeg 인코더 프리셋 추가 (최우선)

`ffmpeg_encoder.cc`에 `ultrafast` + `zerolatency` 프리셋을 추가해야 함:

- 이는 C3와 동일한 인코딩 설정을 적용하는 것으로, 가장 큰 효과가 예상됨
- 프레임 크기 감소 및 인코딩 지연 최소화로 폰 측 디코딩 부하가 크게 줄어들 것으로 기대됨

### 5.2 Livestream 큐 크기 증가

`livestreamRoadEncodeData` 큐 크기를 2MB에서 4MB 이상으로 증가:

- 현재 2MB는 프리셋 없는 인코딩의 큰 프레임을 감당하기에 부족함
- 프리셋 추가와 함께 적용하면 백프레셔 발생 확률을 크게 낮출 수 있음

### 5.3 코덱 선택 방식 안정화

코덱 선택을 정적으로 변경하거나, 변경 시 키프레임 강제 삽입:

- 매 프레임마다 코덱을 결정하는 현재 방식은 스트림 안정성을 저해함
- 최소한 코덱 변경 발생 시 키프레임을 강제 삽입하여 디코더 desync를 방지해야 함

## 6. 추가 검토 필요 사항

다음 항목은 추가 조사가 필요함:

- **C4 기기별 encoderd 실제 사용 인코더 확인**: V4L과 FFmpeg 중 어떤 인코더가 실제로 사용되는지 기기별로 확인 필요
- **livestreamRoadEncodeData 서비스 존재 여부**: 기기별로 해당 메시징 서비스가 실제로 활성화되어 있는지 확인 필요
- **Bootstrap 프로파일에서 카메라 relay 최소 시작 검토**: `p1c4` 등 bootstrap 프로파일에서도 카메라 relay를 최소한으로 시작하여 검은화면 문제를 방지할 수 있는지 검토 필요
